## STARTUP SEQUENCE
> Run this checklist at the start of EVERY session — no exceptions.

```
STEP 1 — GROUND IN THE REPO
  [ ] tree -L 3 (or equivalent) — read the full file structure
  [ ] Read README.md, CLAUDE.md, or any root-level spec
  [ ] Read package.json / pyproject.toml / go.mod / Cargo.toml — identify stack. If none exist, note stack is unknown and proceed.
  [ ] Answer internally: What does this platform DO? Who is the target user?

STEP 2 — CHECK FOR EXISTING DOCS (generated by a previous run)
  [ ] Does docs/research/FEATURE_MATRIX.md exist?
        YES → read it, load current competitor state
        NO  → it will be generated in this session (see §DOC-GEN)

  [ ] Does docs/research/GAP_ANALYSIS.md exist?
        YES → read it, identify highest-priority open gap
        NO  → it will be generated in this session (see §DOC-GEN)

  [ ] Does docs/exploration/CODEBASE_AUDIT.md exist?
        YES → read it, check what has changed since last audit
        NO  → run audit this session (see §3)

STEP 3 — ANNOUNCE PLAN
  Before executing anything, output:
  "SESSION PLAN: [what I will do this session and why, in 3-5 bullets]"
  Human-present mode: Wait for explicit approval ("go", "proceed", "ok") before executing.
  Autonomous mode: Output the plan, then proceed immediately without waiting.
  How to detect mode: Human-present = TTY attached, interactive shell, user is watching.
  Autonomous = no TTY, running via cron/CI/background script, or harness has auto-accept enabled.
  When uncertain, default to HUMAN-PRESENT (safer — ask before acting).

STEP 4 — EXECUTE (follow §1 → §2 → §3 → §4 in order, starting where docs left off)
  If this is the first session and no docs exist, run §1 → §2 → §3 in full before §4.
  If docs exist, skip completed steps and resume from the highest open P0 gap.

STEP 5 — UPDATE DOCS AND DELIVER QA REPORT (mandatory before ending any session — see §DOC-GEN)
   Include all work completed this session; write "(none)" if no implementation occurred.
   If any feature was implemented this session, its QA report MUST be delivered inline to the user.
```

## Definitions & Disambiguation
  - **Major work block**: A focused unit of work that changes product behavior or architecture. Examples: adding a new feature, refactoring auth flow, running full competitor analysis. NOT a major work block: fixing a typo, updating a README, tweaking a CSS color, running `npm audit fix`.
  - **Confirm**: Verifiable by artifact. Examples of valid proof: terminal output showing test pass/fail, screenshot of UI behavior, git diff showing doc update, CI pipeline result. Examples of INVALID proof: "should work", "I think it's done", "tested mentally".
  - **Gap**: Anything classified ❌ or 🚧 affecting parity or surpass goals. Gaps must have GAP-XXX IDs. ID assignment: check `docs/research/GAP_ANALYSIS.md` for the highest existing ID and increment. If the file doesn't exist yet, start at GAP-001. Never reuse a closed gap's ID.
  - **Research**: Links, notes, and decisions backing implementation choices. Research MUST precede coding for P0/P1 work. Time-box: max 30 min per gap before starting implementation. If research is blocked (paywall, dead links, no data), document "RESEARCH BLOCKED — reason" and proceed with best available info.
  - **Feature**: A user-visible capability or measurable improvement. Avoid calling internal refactors "features" unless they change user-facing behavior or performance.
  - **Announce plan**: Output a short, 3–5 bullet summary. Human-present mode: wait for approval ("go", "proceed", "ok"). Autonomous mode: proceed immediately.
  - **Standalone lines**: If a line looks like code or a title but is regular prose, treat it as Markdown text (do not assume template syntax).

### 2.2 User Pain Point Mining

Before implementing any feature, check what users hate about competitor versions:
- Reddit: search `r/[industry]` + competitor name + "problem", "hate", "wish", "broken"

- GitHub Issues: competitor repos, filter by "enhancement" + "frustration" labels

Every user complaint = a design requirement for our version.

## §4 — IMPLEMENTATION PROTOCOL

### 4.1 Priority Order — Non-Negotiable

```
P0 FIRST. Always. No P1 work while any P0 is open.
P1 SECOND. Surpass, don't just match.
P2 THIRD. 20% capacity reserved. These become your moats.
```

### 4.2 Per-Feature Checklist
Before touching code for any P0 or P1 feature, confirm:

```
[ ] Gap is documented in GAP_ANALYSIS.md with a GAP-XXX ID
[ ] Research is written in docs/decisions/[feature].md
[ ] At least 3 implementation options were evaluated (or fewer documented with rationale)
[ ] Selected approach is documented with rationale
```

P2 features: research is optional but recommended. If skipped, document why in the sprint notes.

After implementation, confirm:

```
[ ] Does not regress any existing tests
[ ] New tests written covering the new behavior
[ ] QA scenarios generated (happy + sad flows) — see §4.4
[ ] QA scenarios executed and passed
[ ] Inline documentation added
[ ] Performance is neutral or better vs. baseline
[ ] FEATURE_MATRIX.md updated (cell moved: ❌→✅ or ✅→⭐)
[ ] GAP_ANALYSIS.md updated (gap marked closed)
[ ] Passes "would a competitor's user switch for this?" test
[ ] QA report delivered to user
```

### 4.3 The Surpass Standard

Do not stop at parity. For every feature:

| Level | Description | Status |
|-------|-------------|--------|
| ❌ Missing | Feature doesn't exist | Never acceptable |
| 🟡 Parity | Matches competitor | Temporary waypoint only |
| 🟢 Better | Measurably superior UX or perf | Minimum real target |
| ⭐ Best-in-class | No competitor matches it | Always aim here |

Ask before closing any feature: **"Is this ⭐, or did we stop at 🟡?"**

**What "⭐ Best-in-class" means concretely — pick at least one:**
- Speed/latency: measurably faster than every competitor benchmark you can find
- UX: user can complete the task in fewer steps than any competitor
- Coverage: handles an edge case or use-case no competitor documents
- Reliability: error rate or uptime metric provably better than public competitor SLAs
- DX: integration takes less code / fewer config steps than nearest alternative

If you cannot point to a specific, measurable dimension where the feature beats all known competitors, it is **not ⭐**. Downgrade to 🟢 and open a new gap.

### 4.4 QA Scenarios

After implementation and before marking a gap closed, generate QA scenarios. Every feature MUST have both happy path and sad path coverage. No exceptions.

#### What counts as a QA scenario

A QA scenario is a concrete, executable test case — not a vague description. Each scenario must specify: inputs, expected behavior, how to verify.

#### Happy path scenarios

Test the feature working as intended:

```markdown
## QA: [Feature Name] — Happy Path

### QA-H001: [Normal usage scenario]
- **Precondition:** [What must be true before this test]
- **Steps:**
  1. [Exact action]
  2. [Exact action]
  3. [Exact action]
- **Expected:** [Concrete observable outcome]
- **Actual:** [Fill during execution]
- **Status:** ✅ PASS / ❌ FAIL

### QA-H002: [Edge case that SHOULD work]
- **Precondition:**
- **Steps:**
- **Expected:**
- **Actual:**
- **Status:**
```

#### Sad path scenarios

Test failure modes, invalid inputs, and error handling:

```markdown
## QA: [Feature Name] — Sad Path

### QA-S001: [Invalid input scenario]
- **Precondition:** [What must be true before this test]
- **Steps:**
  1. [Provide invalid/missing input]
  2. [Trigger the action]
- **Expected:** [Clear error message / graceful degradation / no crash]
- **Actual:** [Fill during execution]
- **Status:** ✅ PASS / ❌ FAIL

### QA-S002: [Boundary / empty / null scenario]
- **Precondition:**
- **Steps:**
- **Expected:**
- **Actual:**
- **Status:**

### QA-S003: [Permission / auth failure scenario]
- **Precondition:**
- **Steps:**
- **Expected:**
- **Actual:**
- **Status:**
```

#### Minimum coverage rules

| Feature type | Min happy | Min sad | Extra required |
|-------------|-----------|---------|----------------|
| CRUD / API | 3 | 3 | Auth failure, invalid body, idempotency |
| UI / Form | 2 | 3 | Empty fields, invalid format, back/refresh |
| Background job | 2 | 2 | Retry, timeout, partial failure |
| Integration | 2 | 3 | API down, timeout, malformed response |
| Data migration | 2 | 2 | Rollback, partial migration, duplicate data |

#### QA report delivery

After executing all scenarios, deliver a QA report to the user. The report MUST be:
1. Printed inline in the conversation (not hidden in a file)
2. Written to `docs/qa/QA_REPORT_[feature-name].md`

The report format (see §DOC-GEN for canonical template):

```markdown
# QA Report: [Feature Name]
> Date: [Date] | Gap: [GAP-XXX] | Verdict: PASS / FAIL / PARTIAL

## Summary
- Total scenarios: [N]
- Passed: [N]
- Failed: [N]
- Blocked: [N]

## Happy Path Results
| ID | Scenario | Status | Notes |
|----|----------|--------|-------|
| QA-H001 | [name] | ✅/❌ | |
| QA-H002 | [name] | ✅/❌ | |

## Sad Path Results
| ID | Scenario | Status | Notes |
|----|----------|--------|-------|
| QA-S001 | [name] | ✅/❌ | |
| QA-S002 | [name] | ✅/❌ | |

## Failures (if any)
| ID | What happened | Expected | Severity | Fix needed |
|----|--------------|----------|----------|-----------|

## Verdict
☐ ALL PASS — gap can be closed
☐ PARTIAL — list blockers before closing
☐ FAIL — do not close the gap, fix failures first
```

**Hard rule:** A gap cannot be marked closed in GAP_ANALYSIS.md until its QA report verdict is ALL PASS. PARTIAL or FAIL means the gap stays open.

## §6 — SUCCESS CRITERIA
> The mission is complete when ALL of these are true.

```
[ ] FEATURE_MATRIX.md: zero ❌ in our column vs. top 3 competitors
[ ] Performance: p95 latency ≤ best competitor on equivalent hardware
```

## HARD RULES

| Rule | No exception |
|------|-------------|
| Read SURPASS.md fully before every session | Yes |
| Read existing docs before writing new code | Yes |
| No code without a documented gap to close | Yes |
| No P1 work while P0 gaps are open | Yes |
| No feature marked done without docs updated | Yes |
| Parity is a waypoint, not the destination | Yes |
| Always verify competitor state — never assume | Yes |


## FAILURE ESCALATION
When a gap cannot be closed in the current session, do not silently leave it open.

| Situation | Action |
|-----------|--------|
| Blocked by missing data / access | Document "BLOCKED: reason" in GAP_ANALYSIS.md, set status 🚧, tag `blocker:data` |
| Blocked by upstream dependency | Split gap into two: unblocked sub-task + blocked parent. Work the sub-task. |
| P0 gap, no path forward | STOP, output STATUS REPORT with "🚨 ESCALATION NEEDED" header, list exactly what human must unblock |
| Research exhausted, still uncertain | Mark gap as `confidence:low`, implement best-available option, note assumptions explicitly in code |
| Time budget exceeded (>2h on one gap) | Timebox output: ship partial work, create follow-up gap GAP-XXX-b, note in STATUS REPORT |
